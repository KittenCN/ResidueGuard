# 03｜采集器、软件归属与残留判断

## 3.1 总原则
来源先分类，记录先保真，再进行软件归属与清理能力判断。文件存在、软件已安装、服务正在运行、后台登记可见、权限有效是五个不同事实，不能互相代替。

采集器按 provider 版本维护夹具。每次适配系统变更，先增加真实但脱敏的样本，再修改解析代码。对于不认识的字段/记录类型，保留 raw record 并锁定修改能力。

## 3.2 应用与执行文件索引
基础范围为 `/Applications`、`~/Applications` 及已获准访问的系统应用位置；另外按实际源记录追踪它指向的路径。用户可补充其他扫描根目录。Spotlight 和 LaunchServices 查询用于增加发现线索，不把查询“未找到”当绝对删除证据。

不默认递归用户全部文档。已挂载外部卷中的关联目录只在用户范围授权后检查，不主动挂载离线磁盘。`/opt/homebrew`、`/usr/local` 等路径中的有效独立程序必须纳入相应服务的存在性核验；不能要求所有软件都有 `.app` 外壳。

读取 Bundle 信息和代码签名而非执行程序。跟踪每一个安装实例，保留 bundle ID、Team ID、designated requirement、真实路径、卷身份、文件身份。签名读取错误不直接判定恶意或已删除。

路径规范化不能简单转小写；遵从对应文件系统的大小写规则。解析 alias/symlink 时检测循环、深度上限、离线卷与权限错误。用于删除时不跟随未验证的符号链接；读取展示路径与安全执行目标分开处理。

## 3.3 LaunchdConfigurationProvider
首期读取：
- 当前用户 `~/Library/LaunchAgents`。
- 共享 `/Library/LaunchAgents`。
- 系统范围 `/Library/LaunchDaemons`。
系统自带 `/System/Library/LaunchAgents`、`/System/Library/LaunchDaemons` 仅可读展示，永不进入修改白名单。这些配置层次参考官方启动文档 [S09]；具体命令行为在 P0 对照本机 man page 确定。

使用 PropertyListSerialization 读取 XML/二进制 plist；设文件大小、嵌套层次和字段长度上限。采集 Label、Program、ProgramArguments、BundleProgram（源类型适用时）、RunAtLoad、KeepAlive、WorkingDirectory、UserName、AssociatedBundleIdentifiers 等；未知字段原样保留，不忽略其可能影响。

不要把文件名当 Label，不把 Label 直接当 bundle ID。不要因为 KeepAlive 不为 true 就认为不是后台启动。某些服务按事件触发，当前没进程不代表没安装。

目标解析规则：Program 优先按实际机制解释；ProgramArguments 的首项/脚本参数需要结合已知启动语义。对于 `/bin/sh -c`、动态展开、复杂 env 包装，标记 `ambiguousPayload`，不可执行它来检测。仅对已知固定格式推导脚本目标，同时将解释器和脚本都保留为目标。

## 3.4 LaunchdRuntimeProvider
用于补充当前可访问域中已注册/运行服务信息。调用本机验证过的 `launchctl` 只读子命令，分别维护用户域和系统域。输出是诊断数据，不视为永久格式。

运行信息缺失可能是服务未加载、查询权限不足、域不存在或解析失败，必须区分。仅当与配置的 Label、域、来源/执行身份相符时建立强关联。重复 Label、配置与运行时目标冲突时禁止自动清理。

配置文件不存在但服务仍有运行时登记时，展示运行时记录；它不是“可以删除的 plist”。后续对其 bootout 能力必须另行验证，首期可只读。

## 3.5 BackgroundTaskProvider
使用官方介绍的 BTM 状态诊断来源；P0 验证本机工具路径、权限、输出和记录类型 [S01]。非管理员扫描先尝试允许的只读范围；权限不足显示补充步骤，不暗中提权。

存储原生记录 ID、类型、关联 App ID/Team ID、来源路径、用户范围、原始状态、父子关系等能读取的信息。未知数值不可臆断为开启或允许。输出包含多用户时按授权作用域过滤，原始数据默认不进入持久日志。

同一配置出现在 BTM 和 launchd 来源中，应建立 `describesSameArtifact` 关系，计划器只执行一次文件操作。删除对应配置是精确来源清理，不等同于删除 BTM 历史。登记历史没有稳定逐项入口时必须保留为 guidedOnly。

禁止把全量后台登记重置用于实现行级“删除”按钮。禁止直接读取/写入私有 BTM 存储格式来追求覆盖。

## 3.6 LoginItemsProvider
以实际支持的 BTM 项目和其他经验证登录项目来源汇总。若需要支持旧式登录项，单独做 P0 实验：仅在公开、可验证机制足够时实现适配器；额外 Automation 授权必须显式说明。

旧式 API、脚本字典、系统设置的屏幕显示都不能预先宣称是所有版本的完整列表。未验证的枚举只标记其已见行，未验证的删除禁用。不得调用本应用的 `SMAppService` 对象假装注销别人的服务 [S02]。

## 3.7 PermissionProvider：分类注册表
每个类别配置 displayName、sourceKind、knownServiceTokens、osApplicability、enumerationCapability、targetedResetCapability、scopeRules、systemSettingsRoute。

token 的历史示例包括 Camera、Microphone、Accessibility、ScreenCapture、AppleEvents 等 [S05]，但必须使用经验证的白名单；不通过扫描私有 framework 导出符号自动生成“支持的全部权限”。UI 名称与 backend token 不一定一对一。

自动化 caller-target 关系、文件夹子项、受限照片/通讯录等状态保留结构。未知 service 放进“其他/未知”，只读显示原始 ID；不能猜一个相近类别进行清理。

## 3.8 LegacyTCCReadOnlyProvider
这是可选兼容模块，不是当前/未来系统的产品基础。只在 P0 测试确认能够合法读取、schema 已识别、用户明确授权的旧版 profile 中启用。macOS 27+ 的基线直接禁用 [S03]。普通用户权限不足和完整磁盘访问不足需精确反馈；root 不自动代表可读。

兼容实现可以识别旧版常见用户/系统数据库位置，但不能在新系统中搜索受保护目录以规避限制。SQLite 使用只读连接、query_only 和 schema 检测，只读取必要字段。处理 WAL 一致性，不使用强行绕过锁的 immutable 打开来获取可能过期状态；不要只复制主 DB 文件忽略 WAL。

任何读取操作不得创建/修改系统 sidecar 文件；无法保证只读连接不发生写副作用或一致性不足时返回不可用。应用自己的 SQLite 与此适配器是两个独立边界。

不要写死“某权限永远属于系统 DB/用户 DB”；按本机真实来源标记 scope。授权枚举与有效权限之间可能有缓存/策略差异，因此显示“记录显示为允许”而非保证当前进程一定拥有权限。

## 3.9 ModernPermissionsGuidanceProvider
当前不可枚举的类别返回 `unsupported` 或 `guidedOnly` 及说明，而不是空数组成功。对于可通过公开 API 获知的本应用自身权限，可以准确显示，但绝不冒充第三方软件清单 [S04]。

可导入用户主动提供的历史快照用于比较；标记来源和时间，不与实时结果混在一起。导入的路径/标识全部是非可信输入，不能直接生成可执行计划。

系统设置页面辅助观察属于后续实验：仅用户主动打开并授权辅助功能后运行；只声明已观察到的行；不以自动滚屏/图像识别承诺完整，不自动点击清理或批准权限。失败直接退回手动指引。

## 3.10 TCCResetAdapter
动作必须由已验证 capability 提供的 service + 客户标识生成，使用固定工具与独立参数，不接受任意 shell 文本。P0 在隔离测试环境验证已安装 app、已真正删除 app、路径型 client、用户/系统范围以及每类权限的行为。

对于找不到 bundle ID、权限不足或不支持的 scope，返回明确失败并转为手动建议；禁止用全类别/全应用重置兜底。该失败风险有开发者一手报告，不能忽视 [S06]。

执行重置不等于自动恢复允许，也不保证系统设置历史行马上消失。执行前注明授权可能重新询问，执行后按可观测证据报告。自动化单条关系若只有宽粒度重置，应阻断原计划并解释扩大影响，不能隐式执行。

不要对本地网络、定位套用猜测的 service；这些机制需要独立处理 [S07][S08]。

## 3.11 残留识别的证据流程
先判定保护/管理限制，再判定归属，再判定存在性，最后判定操作能力。

步骤 A：从源记录获取声明的 app、helper、执行目标与卷信息。
步骤 B：查询完整扫描范围内的安装实例，验证指向路径与有效替代路径。
步骤 C：检查强关联的合法独立执行文件、共享 owner、运行时实例、正在安装/迁移迹象。
步骤 D：区分 ENOENT 与 EACCES/EPERM/离线/超时；对于相对路径或动态目标保留未知。
步骤 E：应用保守分类规则，记录每条证据来源与时间。

高可信残留至少同时满足：
1. 有足够强的归属/目标证据，不是按名字猜测。
2. 应用及该登记的实际有效载荷均已不存在，或该类记录的权威标识解析有足够失败证据。
3. 原存储位置可访问且相关卷在线；扫描已覆盖其已知替代安装位置。
4. 没有仍安装的同身份副本、有效共享 owner、有效运行实例或合法独立程序等反证。
5. 不在废纸篓、不在安装更新稳定期、不存在会改变结论的访问/解析缺口。
6. 本轮稳定复核与执行前复核均通过。

旧路径缺失 + Spotlight 未命中并不足够。没有强归属、无安装历史且全盘也不可能完整搜到时应保守为疑似；这会减少红色条目，但比误删好。

建议应用移动/卸载变化的去抖稳定窗口为 5 秒、计划有效期 120 秒，均为可调整设计值。稳定窗口不是“安装绝不会更久”的保证；存在更新进程/临时目录迹象仍需判未知。

## 3.12 执行前身份复核
比较源文件资源身份、内容 hash、Label/目标、卷身份、修改时间和当前归属。发现新安装副本、用户恢复软件、文件被替换或能力 profile 变化，立即失效当前计划与确认。

文件在原地但内容变了，不允许继续按旧计划清理。已被其他程序清理则报告“已不存在，跳过”，不是再次删除一个新出现的同名对象。对于 service-only 目标也要复核运行时身份，不只比较文件指纹。

## 3.13 数据覆盖标准
每个来源统计原始记录数、可解析数、未知数、重复观察数和被权限阻断的区域。必须能解释最终表格行数的来源。数据源只能观测一部分时，“成功列出已见记录”和“完整列出整个分类”必须在 UI 和报告中区分。
