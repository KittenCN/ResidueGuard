# 07｜构建、测试、签名、分发与运维

## 7.1 环境确认
在用户真实 Mac 上先运行只读脚本。记录 `sw_vers`、`uname -m`、开发者目录、Xcode/Swift/SDK 版本；未知实际 OS 时不从浏览器 User-Agent 猜测。

完整 Xcode 需要与宿主系统兼容；选择已安装的合适稳定版本，具体版本在项目中固定 [S12]。Swift 6 为 language mode，编译器精确版本另行记录，不能把两者混称。初始 deployment target 建议 macOS 14，使用更高版本 API 必须加 availability 与能力降级。

开发机器与兼容性测试机器可以不同。macOS 27 和旧版分别验证；不为更广权限读取要求用户关闭保护或降级系统。

## 7.2 项目创建
先检查 git 是否已有仓库；没有才在当前项目根 git init，不创建嵌套仓库。创建可生成 .app 的 Xcode 工程、共享 scheme、独立核心 Package 和测试 targets。固定 bundle ID 和主应用安装/测试路径，避免每次运行换身份造成调试混乱。

项目代码不依赖私有 framework、不请求无关 entitlement。读取不到的权限信息应反映能力不足，而不是随意加一组不存在的 entitlement。

## 7.3 构建入口
P1 完成工程后提供 `script/build_and_run.sh`，负责停止本项目自己的旧运行实例、构建指定 macOS scheme、启动新 .app；绝不停止别人的服务或以 root 启动 GUI。可选 `--logs`、`--verify`、`--debug` 仅针对本项目进程。

本任务包没有伪造该脚本，因为目前没有真实工程和可运行 target。Codex 应使用已安装 build-macos-apps/build-run-debug skill 的规范，读取它指定的 run-button bootstrap 后配置 `.codex/environments/environment.toml`。未读取实际契约前不猜配置字段；脚本不存在时不添加会失败的 Run 按钮。

App 使用系统 .app 启动路径，不能直接执行 SwiftPM GUI 的裸 binary 并据此认为图形界面测试完成。核心单元测试可通过 Swift Package 独立运行。

## 7.4 CI 与测试分层
核心纯逻辑测试可以在支持其依赖的环境运行；只支持 macOS 的模块必须在 Mac runner。xcodebuild 编译与 UI、helper、TCC 行为是不同级别的验证，分别报告。

普通 CI 禁止操作真实系统隐私设置或共享服务。需要 mutation 的 job 明确隔离、使用自有测试 app/agent、可回滚磁盘与专用身份；不得让 CI 自动重置管理员日常环境的全部权限。

建议输出 `docs/validation/test-results-<date>.md`，包含命令、退出码、失败类别、环境和未执行项。不要仅保存截图作为系统正确性的证据。

## 7.5 本地签名与发布签名
本地编译成功、开发签名通过和可公开分发不是同一件事。P0/P1 可使用合适的开发签名进行普通 UI 开发；涉及 helper 信任关系和隐私身份稳定性时必须有能够验证的签名策略。

发布目标为 Developer ID + Hardened Runtime + 公证 [S11]，先签 nested helper，再签主 bundle，验证后打包并公证/staple。具体流程使用目标工具链的官方命令，不把证书、私钥或 App Store Connect 凭据写进仓库。发布说明列出支持的实测 OS profile。

Mac App Store 对 sandbox、自包含与提权有明确限制，因此此完整版工具不以商店分发为首期路线 [S10]。不意味着所有只读系统工具都不能上架；未来可单独设计能力受限版本，但不是本项目当前目标。

## 7.6 首次运行与最小权限
无授权启动也应能展示 GUI、能力说明和可读取的基础扫描。不要在启动时申请辅助功能、摄像头、麦克风、自动化和完全磁盘访问“一揽子全开”。

需要高级来源时用户主动选择，并解释权限的用途、读取范围和剩余限制。系统权限由用户在系统提供的界面批准；工具不能自行给予授权。

主 GUI 的权限不会自动等于 helper 的权限，helper 身份也不能拿来绕过 GUI 的隐私限制。TCC 重置按真实账户作用域执行，不能简单把所有命令 sudo 之后假定仍作用于当前用户。

## 7.7 能力版本管理
能力矩阵带 schemaVersion、providerVersion、OS build 和证据路径。发布包内写能力默认关闭，只有经过验证的 policy profile 才打开对应来源/动作。

源输出格式变化、签名握手变更、OS 主版本升级、schema 检测失败都可触发 readOnly。不能仅靠数字版本比较就假设未来系统行为相同。升级后先只读复核旧计划，禁止沿用升级前的执行 token。

## 7.8 自身后台项管理与卸载
设置页明确显示：本工具是否随登录启动、是否存在特权 helper、版本、批准状态、何时安装、如何移除。默认不注册登录启动，不启用持续监控。

卸载准备流程：停止本工具自己的扫描/任务；用受支持服务管理流程撤销自身 helper/登录服务；验证撤销状态；让用户选择保留操作历史/备份还是删除本应用私有数据。不要因为清理软件要自卸载，就去删除其他软件共享数据或系统数据库。

正在进行清理时不能直接自卸载；先安全停止并记录。用户直接把 app 拖到废纸篓时的行为需要真实测试，不能承诺所有 OS 会自动清掉 helper。用户手册提供恢复安装后撤销自身服务的流程。

## 7.9 用户可理解的发布说明
每版至少列：可枚举来源、可直接清理类型、只能引导的权限类别、支持的已测试系统、可能需要系统刷新/再次登录的显示变化、恢复范围、日志和网络策略。

不写“清理所有卸载残留”“彻底修复权限”“100% 不误删”“清理后 Mac 立刻提速”。它们都不是本项目能凭现有证据承诺的事情。
