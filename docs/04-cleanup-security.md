# 04｜确认状态机、清理事务与安全约束

## 4.1 威胁模型与边界
需要防范用户误选、应用搬移/重装导致旧计划失效、恶意路径/符号链接、伪装归属、篡改请求、重复执行、备份失败、权限范围扩大、工具输出变化以及执行中崩溃。系统管理员或同一用户已有完全控制权的恶意进程不在本工具可彻底防御的承诺范围内；仍须尽量限制 helper 被当作提权代理。

目标是可审计、低误操作的系统工具，不是安全产品认证。红色残留不是恶意软件判断；两次确认也不是允许绕过保护的安全例外。

## 4.2 真实影响集合
`actualImpact(plan)` 必须包含每一步实际可能改变设置的软件身份、配置文件、运行服务、权限关系及用户范围。不能只取 UI 选中的行。

一个底层操作可能影响多个表格行；一个表格行也可能对应多个操作。先归一、去重、扩展影响，再计算确认次数。无法界定实际影响时，结果为 blocked，而不是提醒一句“有风险”后照做。

例子：用户勾选已卸载软件 B 的一条自动化被控关系，但当前 backend 只能重置仍安装软件 A 的全部自动化权限。原始“全红计划”无效；显示扩大范围及涉及 A 的真实关系，用户明确改选后重新生成双确认计划。无法列清扩大范围则不提供执行。

## 4.3 确认策略
```text
if selectedRecords.isEmpty:
    noAction
else if any operation is unsupported/protected/managed/ambiguous:
    blocked
else if actualImpact contains unknown/unverified identities or unbounded scope:
    blocked
else if every affected application is highConfidenceOrphan:
    oneInAppConfirmation
else if any affected application is installed:
    twoIndependentInAppConfirmations
else:
    blocked
```

此策略的“已安装”也包括合法独立 CLI 软件。共享组件仍被其他应用依赖时 v1 默认保护，而不是仅增加确认。程序不以源行颜色替代策略判断。

## 4.4 状态机
```text
idle
 → selectionMade
 → planning
 → planReady
 → firstConfirmationPresented
 → firstConfirmed
    ├─ one-confirm → consentComplete
    └─ two-confirm → secondConfirmationPresented → secondConfirmed → consentComplete
 → authorizationIfNeeded
 → finalRevalidation
 → backupsPrepared
 → executing
 → verifying
 → completed / partial / failed / cancelled
```

“检查所选操作”不计入确认。两次确认必须独立渲染和等待独立用户事件；不能把同一张表单的复选框和一个按钮算两次。第二次要求输入指定风险短语，并且不能由第一次事件自动触发。

系统密码/Touch ID、系统对后台 helper 的批准均是额外系统步骤，不抵扣产品确认次数。计划含管理员步骤时，执行任何修改前先完成整个计划所需的授权，用户拒绝后不先偷偷清理用户级部分。

授权完成之后仍需重新核验指纹。所有不可变计划内容纳入摘要；改变勾选、操作类型、影响范围、源指纹、存在判定、能力 profile 或策略版本，都使之前的确认失效。单纯 GUI 排序不改计划。

默认计划有效期建议 120 秒；过期重新扫描/复核并重新确认。长时间等待管理员认证导致过期，返回预览，不默默延长 token。

## 4.5 清理交易不是全系统 ACID
多个操作源无法形成单个系统数据库事务，因此采用逐步日志和补偿计划（saga）。每步保存准备、执行、验证及失败状态；执行失败时不会谎称“全部回滚”。

每个动作必须明确前置条件、预期变化、验证方式、失败后的停止规则及可否补偿。相关依赖链失败则停止其后续步骤；不相关动作是否继续由用户在第一次确认中选择的批处理策略决定，v1 默认遇到修改失败停止后续动作。

## 4.6 典型用户 LaunchAgent 清理
1. 验证来源、Label、加载域、执行身份与归属；确保当前用户有权处理。
2. 生成只包含选中对象的计划，完成要求的确认。
3. 重新读取源指纹与所有影响对象的存在状态。
4. 将原始配置及必要元数据备份至安全区域，验证内容 hash 与备份可读性，记录 manifest。
5. 若服务存在，调用经过本机验证的精确 bootout 机制；若服务已确定未注册，可以记录无需卸载。无法确定/卸载失败则不继续移除配置。
6. 隔离该配置至备份/隔离区；不直接永久删除，不删除目标应用或其数据目录。
7. 验证原路径状态、隔离文件身份、服务状态；复扫相关来源。
8. 分别报告文件、运行时和后台登记结果。历史 UI 未刷新时标记待确认，不为了“好看”进行全局重置。

不在生产文档预置一键 bootout 批处理脚本。确切命令语义由 P0 的目标系统手册和安全夹具实验确定，最终在 typed adapter 中固定。

## 4.7 共享/系统级启动配置
特权 helper 只处理明确允许的共享配置根。必须核验目录与文件的 owner、权限、类型，以及源登记与运行服务的一致性。系统自带配置和受管理记录排除。

共享 LaunchAgent 可能影响多个登录用户。预览必须说明配置是机器共享的；活动会话状态无法完全验证时，首期阻断即时清理，而不是假装只影响当前账号。系统 daemon 的作用域也须明确显示为整个机器。

不要读取其他用户家目录的隐私信息来补齐列表。对管理员模式仍无法安全界定的共享项，给出手动方案。

## 4.8 权限重置交易
权限重置的历史授权不可通过复制数据库安全恢复，因此显示“不可自动恢复原授权，未来可能需要重新允许”。只允许精确白名单 service + 已验证身份 + 已知作用域的操作。

命令失败后不扩大范围；找不到已卸载 bundle ID 时停止，保留原错误和手动建议。命令成功但无法读取后置状态时结果为 issued/unverified，不能显示“已清除系统列表中的条目”。

拒绝项也可以是历史记录；删除一个拒绝记录可能使未来再次请求，并非天然更安全。预览要把“重置”而非“提升隐私”作为真实后果。

## 4.9 特权 helper 设计
通过本应用自身受支持的 ServiceManagement 安装/批准流程提供 helper [S02]。仅在用户启动需要管理员权限的功能时引导安装。服务可被 launchd 按需唤起，不设置无必要的常驻轮询；它在软件界面与自卸载流程中必须可见。

IPC 最少只暴露以下语义操作：查询 helper 状态、为已知来源准备计划、执行一次性计划 token、查询执行状态、为已知备份准备恢复。不得暴露 `run(command)`、`delete(path)`、`write(file,data)`、任意 shell 或任意 sudo 转发。

helper 应从已验证的连接身份获取调用方，校验签名 requirement / bundle 身份 / Team 身份 / 用户与会话，拒绝同 Team 但不同授权程序。使用目标 SDK 中有文档支持且实际测试过的 code-signing/audit identity 方法；不凭记忆杜撰某个 NSXPCConnection 属性，也不使用 KVC 或私有 API 读取 audit token。

P0/P4 必须提交握手与签名验证的实际代码依据、SDK 可用性和攻击测试。仅检查 PID、可执行路径字符串或由 GUI 自报 bundle ID 不合格。稳定开发签名与发布签名分 profile，但开发模式也不能变成任意进程可连接。

helper 独立核验源类型、根目录、目标身份、指纹、策略版本、授权权利、token 生命周期和实际影响。GUI 的 `confirmed=true` 不是系统授权证明；UI 确认由可信客户端管理，helper 则强制自己的操作白名单与权限策略。

一次性计划 token 绑定调用方、scope、摘要、nonce、到期时间。执行状态持久化，重复 token 返回同一结果或明确拒绝，不再执行第二次。

## 4.10 路径与文件安全
- 绝对路径规范化不等于安全，必须核验每级目录和文件身份。root 操作只接受 root 控制、无不安全写权限的允许目录，不写任意用户路径。
- 读取使用不跟随未验证链接的模式；以目录 fd 为锚，结合 `openat`/`fstat`/文件类型和 owner 校验等公开系统能力。API 的正确用法在实现和测试中证明。
- 检测 symlink、hardlink、设备文件、socket、路径遍历、别名循环与大小写冲突；非预期类型阻断。
- 源 file handle 指纹、计划指纹和隔离后文件指纹必须一致。仅在先 check 后按字符串 rm 的实现不通过安全审查。
- 任意 rename/copy/remove 序列都需评估 TOCTOU。对于非 root 可写父目录，不能声称简单 lstat + rename 具有不可竞争的安全性；采用已验证策略，身份异常立刻停止，不删除异常对象。
- 备份目的地由执行侧生成并控制，manifest 不接收用户任意路径；跨卷复制仅在元数据/内容验证后移除原对象。失败留下可诊断状态，不绕过备份。

## 4.11 备份、隔离与恢复
保存原始路径、源身份、hash、文件内容、文件模式、owner/group、必要扩展属性/ACL、原服务登记状态、所属计划和操作时间。敏感文件不进入 git 或普通日志。

用户级备份目录限制当前用户访问；特权备份 root-owned，由 helper 自己核验。默认保留 30 天是建议产品策略，但达到时间不直接后台永久删除：在设置中提示并由用户确认清空，或者由用户先明确开启到期清除策略。

恢复先检查原路径是否已存在、新软件版本是否已经安装、备份是否被篡改、权限元数据是否仍合适。冲突不覆盖。恢复文件后不自动重新启动服务；重新加载需要独立明确操作和当前验证。备份中的旧路径可能不再有效，因此恢复也需计划和影响预览。

权限重置仅保留审计信息，不提供“恢复旧授权”假按钮。后台历史刷新不是备份能保证恢复的对象。

## 4.12 日志、导出与隐私
普通统一日志默认隐藏用户名、完整敏感路径与所有权限清单。调试输出主动启用、有期限；导出报告明确选择是否包含路径、签名标识等信息。

CSV 导出对以 `= + - @` 等可能触发表格公式的用户字段进行安全处理，正确引号/换行转义；JSON 保留结构且不注入可执行脚本。导出的报告永远不作为直接执行命令源。

默认完全离线，不上报软件列表/权限记录；未来更新检查也要与扫描数据分离，并且不是首期扫描前提。

## 4.13 恢复与崩溃原则
应用启动时检测未完成 journal：展示上次已完成步骤和待处理项，先只读复核。不得为了“自动修复”重新执行删除、重新启用后台服务或自动批准权限。自动恢复只可恢复本应用自身一致性，涉及系统状态的补偿仍需明确计划。
